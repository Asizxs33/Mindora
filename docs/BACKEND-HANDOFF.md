## 1. Главное для разработчика

**Начинай от свежей `main`. Авторизация уже реализована — её не нужно писать заново.** В `main` уже объединены backend друга, профиль пользователя, AI-уроки и синхронизация бюджетного черновика. Ветка дизайна содержит более новые изображения персонажей, но пока не содержит этот backend.

Основная недостающая часть — **личные курсы и полный прогресс в аккаунте**. Сейчас есть один текущий AI-план в браузере, а облако сохраняет только профиль и бюджетный черновик. Поэтому новый вход, новый курс и продолжение старого курса ещё не образуют единую систему.

Первый рабочий результат backend-разработки:

1. Пользователь регистрируется или входит.
2. Если курсов нет, видит `What would you like to learn?`.
3. Создаёт курс, который получает собственный ID и сохраняется за его аккаунтом.
4. Проходит короткий урок: объяснение → пример → задание → ответ → результат.
5. Закрывает вкладку и продолжает с того же места, в том числе на другом устройстве.
6. Нажимает `New course`: старый курс остаётся сохранённым.
7. После перерыва более 24 часов получает короткое повторение.
8. Завершает весь курс и получает сертификат о прохождении.

Не очищать данные при каждом коммите или деплое. **Обновление приложения и сохранение учебного прогресса — независимые процессы.**

## 3. Как безопасно объединить работу двоих

1. Сохранить свои изменения отдельным коммитом.
2. Выполнить `git fetch origin`.
3. Создать рабочую ветку от актуальной `origin/main`, например `feat/account-courses`.
4. Продолжать backend на этой базе. Ветка `feat/learning-experience` уже включена в проверенную `main`.
5. Перенести новые изменения дизайна после общего предка `80df9f9` обычным merge или выборочным переносом коммитов с просмотром diff.
6. При конфликтах сохранить backend, зависимости, API-обработчики и обработку аккаунта из `main`; визуальные изменения проверить отдельно.
7. Открыть PR, пройти проверки и объединить после просмотра вторым участником.

Не заменять дерево `main` целиком содержимым старой frontend-ветки: так потеряются `backend/`, `api/` и интеграция сессий.

Разделение работы описано в [TEAM.md](TEAM.md): дизайн — `ui/`, состояние и поведение — `core/`, сервер — `backend/` и `api/`. Для изменений логики и документации используй `feat/*`: существующий CI ограничивает ветки `design/*` файлами `ui/`.

## 4. Запуск и окружение

### Текущий стек

- Vanilla JavaScript, HTML и CSS; React не используется.
- Node.js; для одинаковой локальной среды и CI использовать Node.js 22.
- Vercel Functions для `/api/*` и статическая сборка в `dist`.
- Neon Postgres и уже подключённый Neon Auth.
- DeepSeek для поиска, генерации и текстовой обратной связи.
- Readability, LinkeDOM и Marked для чтения открытых материалов.

В проверенной `main` установлен `@neondatabase/auth@0.7.0-beta`. Существующий код импортирует `@neondatabase/auth/server`. Сначала сохранить работающий контракт и lockfile. Смена SDK — отдельное изменение с проверкой сессий, а не обязательный шаг для курсов.

### Переменные сервера

| Переменная | Для чего нужна | Где задавать |
| --- | --- | --- |
| `DATABASE_URL` | Профили, бюджетные черновики, AI-лимиты; затем курсы и прогресс | Локальная среда; Vercel Preview / Production |
| `NEON_AUTH_BASE_URL` | Auth endpoint нужной Neon-ветки | Только сервер |
| `NEON_AUTH_COOKIE_SECRET` | Секрет cookie для существующего SDK; минимум 32 случайных символа | Только сервер, стабильное значение для окружения |
| `DEEPSEEK_API_KEY` | Генерация уроков и review | Только сервер |
| `PORT` | Необязательный локальный порт; по умолчанию 4173 | Локально |
| `VERCEL` | Служебный признак Vercel для обработки IP-лимита | Платформа выставляет сама |

В текущем backend нет использования Google/Gemini API key. Наличие такого ключа само по себе не включает существующую DeepSeek-интеграцию.

`DATABASE_URL` и `NEON_AUTH_BASE_URL` должны относиться к согласованному окружению. Для Preview лучше использовать отдельную Neon-ветку. У Neon Auth конфигурация и endpoint зависят от ветки: [официальный обзор Neon Auth](https://neon.com/docs/auth/overview).

### Порядок настройки

1. Проверить доступ к правильному Neon-проекту и ветке.
2. Проверить, что Auth включён именно для неё; взять её Auth URL.
3. Указать разрешённые адреса приложения в настройках Auth: локальный origin и нужные Vercel-домены. Не путать `localhost` и `127.0.0.1`.
4. Настроить переменные отдельно для Preview и Production; секреты не вставлять в `ui/`, `core/`, MD или Git.
5. Установить зависимости из lockfile.
6. Запустить сервер с переданными переменными.
7. Проверить `/api/account`, затем реальную регистрацию, вход и сохранение профиля.

Пример локального запуска из корня актуальной `main`:

```powershell
npm ci
node --env-file=.env.local server.mjs
```

Файл `.env.local` создать локально с перечисленными именами и своими значениями. Он игнорируется Git. `npm start` тоже работает, если переменные уже переданы процессу: сам `server.mjs` `.env` автоматически не читает.

Открыть `http://127.0.0.1:4173/`. Мутации API требуют совпадающий `Origin`, поэтому тестировать через тот же origin приложения или задавать соответствующий заголовок в API-клиенте.

Проверки после изменений кода:

```powershell
npm run check
npm test
node scripts/build.mjs
```

В старой версии `TEAM.md` встречается фраза, что зависимости устанавливать не нужно. Для актуальной `main` с backend нужен `npm ci`, как указано в её README.

## 5. База: уже реализованные таблицы

| Таблица | Поля | Назначение |
| --- | --- | --- |
| `public.mindora_profiles` | `user_id text PRIMARY KEY`, `profile jsonb NOT NULL`, `updated_at timestamptz NOT NULL DEFAULT now()` | Профиль; JSON должен быть объектом |
| `public.mindora_budget_drafts` | `user_id text PRIMARY KEY`, `workspace jsonb NOT NULL`, `revision integer NOT NULL DEFAULT 1`, `updated_at timestamptz NOT NULL DEFAULT now()` | Один бюджетный workspace на пользователя; JSON-объект; revision > 0 |
| `public.mindora_plan_quota` | `day date PRIMARY KEY`, `total integer NOT NULL`, `visitors jsonb NOT NULL` | Общий суточный лимит AI и счётчики посетителей |

Код создаёт отсутствующие таблицы при первом соответствующем запросе под advisory lock. Используются параметризованные SQL-запросы, `REVOKE ... FROM PUBLIC` и включение RLS.

**Граница доступа сейчас находится в API:** он проверяет сессию и фильтрует SQL по её `user.id`. Явных пользовательских RLS policies и `FORCE ROW LEVEL SECURITY` в проверенном коде нет. Привилегированное подключение владельца может обходить RLS — нельзя считать одно `ENABLE ROW LEVEL SECURITY` достаточной изоляцией.

Пароли и сессии обслуживает Neon Auth. Не создавать собственную таблицу паролей и не сохранять пароль в `localStorage`. Не менять внутренние таблицы Auth вручную.

Новые изменения схемы оформлять отдельными версионированными миграциями, сначала проверять на тестовой ветке базы. Существующие аккаунты, профили и черновики сохранить.

## 6. База: что добавить для полного продукта

Ниже **предлагаемая схема, ещё не реализованная этим документом**. Для первой версии достаточно JSON-содержимого курса с устойчивыми ID; не нужно сразу разбивать каждый текстовый блок на отдельную таблицу.

### 6.1 `mindora_courses` — личные курсы

| Поле | Тип / правило |
| --- | --- |
| `id` | UUID, первичный ключ, создаёт сервер |
| `user_id` | text, только из проверенной сессии |
| `title`, `goal` | text, проверенные длины |
| `language`, `level` | согласованные значения; интерфейс по умолчанию `en` |
| `daily_minutes` | integer: 5 / 10 / 20; это длина сессии, не всего курса |
| `template_id`, `template_version`, `mentor_id` | ссылки на внутренний шаблон и разрешённого персонажа |
| `status` | `queued`, `generating`, `ready`, `failed`, `archived` |
| `content` | jsonb: уроки, блоки, задания, критерии, источники; пуст до готовности |
| `content_version`, `schema_version` | integer; версия учебного материала и формата данных |
| `created_at`, `updated_at` | timestamptz |

Индекс по `(user_id, updated_at DESC)`. Для составных связей предусмотреть уникальность `(id, user_id)`.

Опубликованное содержимое курса фиксируется на время прохождения. Повторная генерация не должна менять ID уже пройденных заданий: либо новая версия с явной миграцией, либо новый курс.

### 6.2 `mindora_course_progress` — точное место продолжения

- `course_id`, `user_id`: первичный/уникальный ключ; составной внешний ключ на курс и его владельца.
- `content_version`: прогресс относится к определённому содержимому.
- `cursor jsonb`: `lessonId`, `activityId`, `pageIndex`, `quizIndex`, состояние выбранного ответа и показанной обратной связи.
- `drafts jsonb`: незавершённые ответы и редактируемые работы по ID задания.
- `completed_activity_ids`: набор завершённых заданий; итоги подтверждает сервер.
- `revision integer`: возрастает при каждом успешном сохранении.
- `last_learning_at`, `updated_at`, `completed_at`: timestamps; последнее поле nullable.

Клиент может отправлять черновик и позицию. Он не может произвольно назначить себе `completed_at`, XP, право на сертификат или прохождение закрытого урока.

### 6.3 `mindora_attempts` — ответы и проверки

- `id`, `user_id`, `course_id`, `content_version`, `activity_id`.
- `answer jsonb`, `feedback jsonb`, `status`: pending / reviewed / needs_retry / completed.
- `idempotency_key`, `created_at`, `reviewed_at`.
- Уникальность `(user_id, idempotency_key)`; повтор запроса возвращает тот же результат.
- Тип проверки зависит от задания: точный ответ, проверяемые критерии практики или явно обозначенная самопроверка.

AI-комментарий сам по себе не является достоверной оценкой. До внедрения оценки не выдавать текстовое пожелание модели за подтверждение правильности работы.

### 6.4 `mindora_learning_events` — учебные дни и огонёк

- `id`, `user_id`, `course_id`, `activity_id`, `event_type`, `occurred_at`.
- `study_date`, `timezone`: дата в выбранном часовом поясе и IANA timezone, например `Asia/Qyzylorda`.
- Уникальный ключ события для защиты от повторной отправки.
- Индекс `(user_id, study_date)`.

Учебный день засчитывается за содержательное учебное действие, а не за открытие сайта. Повторное открытие/проверка одного завершения не увеличивает XP. Правило изменения часового пояса должно быть явным; не пересчитывать историю бесконтрольно по часу устройства.

### 6.5 `mindora_entitlements` — бесплатный и demo-доступ

- `user_id` — первичный ключ.
- `plan`: free / demo_plus.
- `free_course_id` — первый выделенный бесплатный курс; сохраняется даже при его архивировании.
- `expires_at` — nullable; срок demo-доступа, если он ограничен.
- `updated_at`.

Право доступа проверяется сервером при создании курса, чтении закрытого урока, отправке ответа и выдаче сертификата. Поле `plan` из браузера не считается доказательством подписки.

### 6.6 `mindora_certificates` — результат всего курса

- `id`, `user_id`, `course_id`, `content_version`.
- `learner_name`, `course_title` — снимки данных на момент выдачи.
- `issued_at`, `verification_code`.
- Уникальность `(user_id, course_id, content_version)`.

Выдача только после серверной проверки обязательных заданий. Скачать повторно можно без повторного начисления достижений. Название — `Certificate of completion`; не обещать аккредитацию.

### 6.7 `mindora_generation_jobs` — генерация без потери результата

- `id`, `user_id`, `course_id`, `idempotency_key`.
- `status`: queued / running / ready / failed.
- `phase`: researching / planning / writing / validating.
- `attempt_count`, `error_code`, `created_at`, `updated_at`.
- Уникальность `(user_id, idempotency_key)`.

Если полный курс не укладывается в один HTTP-запрос, нужна настоящая очередь/задача с сохранением состояния. Не запускать незавершённую работу через непроверенный «fire-and-forget» после ответа serverless-функции.

### Общие правила схемы

Все запросы ограничены владельцем из сессии; UUID курса не является разрешением на чтение. Внешние ключи предотвращают привязку прогресса/ответа к чужому курсу. JSON валидируется сервером по версии схемы. Добавить ограничения размеров, индексы владельца, транзакции для завершения и учёт применённых миграций. Не хранить крупные изображения в JSON базы: хранить пути и метаданные ресурсов.

Новые поля профиля (`timezone`, состояние onboarding, `activeCourseId`) согласованно добавить в серверную валидацию, хранение и клиентский контракт: текущий обработчик удаляет неизвестные поля. Одного добавления свойства в форму недостаточно. `activeCourseId` разрешать только для курса этого пользователя.

## 7. Уже существующие API — сохранить контракт

### `/api/account`

**GET** — сессия и профиль:

```json
{
  "available": true,
  "user": { "id": "auth-user-id", "name": "Alex", "email": "alex@example.com" },
  "profile": { "name": "Alex", "age": null, "gender": "", "interests": ["Design"] }
}
```

Без входа `user` и `profile` равны `null`. При отсутствующих настройках Auth GET возвращает `available:false`, а не фиктивный вход.

**POST** поддерживает:

```json
{ "action": "signup", "email": "alex@example.com", "password": "example-only-password", "name": "Alex", "age": null, "gender": "", "interests": ["Design"] }
```

```json
{ "action": "signin", "email": "alex@example.com", "password": "example-only-password" }
```

```json
{ "action": "signout" }
```

Нормальный результат: `{ok:true,user,profile}`. При регистрации возможны отдельные состояния:

- `verificationRequired:true`, `user:null`: нужно подтвердить email; не показывать, что аккаунт уже вошёл и профиль сохранён.
- `profilePending:true`: сессия создана, профиль не удалось сохранить; повторить сохранение через PUT, не создавать аккаунт заново.
- `SESSION_UNCONFIRMED`: новая сессия после входа/регистрации не подтверждена.

**PUT** — обновить профиль текущей сессии:

```json
{ "name": "Alex", "age": 20, "gender": "prefer_not_to_say", "interests": ["Design", "Programming"] }
```

Текущая валидация: имя 1–80 символов; возраст `null` или целое 1–120; интересов до 8, каждый 1–40 символов, без дублей по регистру. Пол: `""`, `woman`, `man`, `nonbinary`, `other`, `prefer_not_to_say`. Email до 254 символов, пароль 8–128. JSON body до 16 384 байт. Изменяющие запросы проверяют origin. Обычные ошибки аккаунта имеют `{error,code}`. Исключение — отсутствие конфигурации: `{available:false,user:null,profile:null}`, HTTP 200 для GET и 503 для POST/PUT.

После подтверждения email на другом устройстве или перезагрузки временные поля onboarding могут потеряться. Нужен сценарий `Finish your profile`, который читает профиль после подтверждённого входа и дозаполняет отсутствующие поля. Возраст и пол остаются необязательными.

### `/api/budget-draft`

- GET: `{draft:null}` или `{draft:{workspace,revision,updatedAt}}`.
- PUT: `{workspace,revision}`. При создании revision = `null`; при обновлении — последняя полученная версия.
- Устаревшая версия → HTTP 409. Нельзя молча перезаписывать работу другого устройства.
- Workspace содержит только бюджетные данные: минуты, progress, step, goal, упражнение, формулу, ответ, баланс и seed.

Это **не API всех курсов**. Сохранить его совместимость, пока бюджетный сценарий явно не мигрирован в общий механизм.

### `/api/learning-plan`

POST:

```json
{ "goal": "Create my first cafe poster", "minutes": 5, "language": "en" }
```

Цель 3–180 символов; минуты 5/10/20; языки en/ru/kk. Ответ `{plan}` с `goal`, `minutes`, `language`, `title`, `outcome`, `steps`.

Шаг содержит `id`, `title`, `instruction`, `task`, `criterion`, `minutes`, необязательный `resource` с URL, названием и изображениями. В текущем результате хотя бы один шаг должен иметь источник.

Сейчас 5 минут дают 2 задания, 10 — 3, 20 — 4. Это **короткая учебная сессия, а не полный многодневный курс**. `backend/course-skills.js` содержит правила для модели, а не 15 готовых шаблонов.

### `/api/task-review`

POST принимает `goal`, `task`, `criterion`, `answer`, `language`. Максимальные длины: 180 / 900 / 320 / 1500 символов соответственно для первых четырёх полей.

```json
{ "review": { "observation": "What worked in your answer.", "nextAction": "One useful next step." } }
```

Сейчас это текстовая обратная связь. Здесь нет выполнения пользовательского кода, оценки загруженного файла, проверки рисунка или серверной итоговой оценки.

Оба AI endpoint сейчас доступны без обязательного входа. Ограничения: origin и общая квота, а не права бесплатного/платного курса. При переводе на аккаунтные курсы проверку сессии и entitlement добавить явно.

## 8. Предлагаемые новые API

**Эти маршруты пока не существуют.** Названия — контракт для согласования frontend и backend.

| Метод и маршрут | Что делает |
| --- | --- |
| `GET /api/courses` | Возвращает только курсы текущего пользователя, их статус и краткий прогресс; не весь контент |
| `POST /api/courses` | Создаёт отдельный курс/задание генерации по цели; проверяет entitlement; принимает idempotency key |
| `GET /api/courses/:id` | Возвращает курс, разрешённые уроки, прогресс, revision и права доступа |
| `GET /api/course-jobs/:id` | Статус генерации; позволяет уйти и вернуться к тому же результату |
| `PUT /api/courses/:id/progress` | Сохраняет курсор и черновик с ожидаемой revision |
| `POST /api/courses/:id/attempts` | Сохраняет ответ, проверяет активность и фиксирует допустимое завершение |
| `GET /api/courses/:id/resume` | Возвращает точный курсор и необходимость повторения |
| `POST /api/courses/:id/recap` | Фиксирует результат повторения, возвращает исходное место продолжения |
| `POST /api/courses/:id/certificate` | Идемпотентно выдаёт сертификат при выполнении требований |
| `GET /api/certificates/:id` | Получение своего сертификата и данных для скачивания |
| `GET /api/entitlements` | Возможность нового курса, бесплатные уроки, demo-доступ |

Для каждого маршрута: проверенная сессия → валидация → проверка владельца → проверка доступа → операция → ответ. Для чужого или неизвестного course ID возвращать одинаковый 404. Запрос без сессии — 401; закрытый по тарифу материал — 403 с отдельным кодом.

Пример сохранения прогресса:

```json
{
  "revision": 7,
  "contentVersion": 1,
  "cursor": { "lessonId": "lesson-2", "activityId": "quiz-2-1", "pageIndex": 0 },
  "drafts": { "quiz-2-1": { "selectedOptionId": "answer-b" } }
}
```

Успех: `{progress,revision:8,savedAt}`. Конфликт: HTTP 409 `{error,code:"PROGRESS_CONFLICT",serverRevision}`. Клиент сохраняет локальный черновик и предлагает восстановить/согласовать версии. Не повторять устаревшую запись как принудительную перезапись.

Единые коды ошибок для нового API: `UNAUTHENTICATED`, `INVALID_INPUT`, `NOT_FOUND`, `COURSE_LOCKED`, `PROGRESS_CONFLICT`, `GENERATION_PENDING`, `GENERATION_FAILED`, `RATE_LIMITED`, `SERVICE_UNAVAILABLE`. UI переводит код в короткий понятный текст. Текущие API пока имеют неодинаковую структуру ошибок — переход делать совместимо.

Обработчики нужно подключить **и к Vercel в `api/`, и к локальному `server.mjs`**. Конкретные файлы для динамических маршрутов создать согласно маршрутизации проекта; одной таблицы или нового `backend/*.js` недостаточно.

## 9. Как исправить «застрял на старом курсе»

Причины в текущем коде:

- `core/plan-controller.js` хранит один `state.learningPlan`.
- Совпадение цели, времени и языка может вернуть существующий план без новой генерации.
- Новая генерация заменяет текущий план и его рабочий контекст.
- `core/app.js` восстанавливает открытый AI-план через `learningPlanOpen`.
- Общий ключ `mindora.workspace.v1` не разделяет весь workspace по аккаунтам.
- Событие `mindora:account-changed` обновляет облачные бюджетные элементы, но не превращает всё локальное хранилище в отдельные аккаунтные курсы.

Нужное поведение:

1. Явно разделить действия `Continue learning` и `New course`.
2. Хранить коллекцию курсов и `activeCourseId`, а не единственный заменяемый объект.
3. Новый курс получает новый ID даже при той же цели, если пользователь выбрал создание заново. Повтор одного сетевого запроса с тем же idempotency key, наоборот, не создаёт дубль.
4. Вход нового пользователя без курсов открывает создание курса; возвращение существующего — его последнюю активность.
5. Смена аккаунта отменяет или игнорирует старые запросы и закрывает приватные данные предыдущей сессии.
6. Локальный кеш разделить по user ID + course ID + версии схемы. Гостевой workspace хранить отдельно.
7. При входе предложить перенести гостевую работу в аккаунт. Не прикреплять чужие/непонятные данные автоматически.
8. Миграцию старого ключа делать один раз, с сохранением исходных данных до успешного переноса. Не сбрасывать прогресс ради исправления стартового экрана.

## 10. Сохранение, повторение и streak

### Сохранение

- Локально сохранять ввод сразу; облако обновлять с небольшой задержкой после ввода и сразу на значимых переходах.
- Курсор сохранять при переходе страницы, выборе/проверке ответа, завершении задания и выходе из урока.
- Показывать честный статус: `Saving…`, `Saved`, `Saved on this device — waiting to sync`.
- Не полагаться только на `beforeunload`: мобильный браузер может закрыть вкладку без этого события.
- Незавершённые записи держать в очереди, привязанной к аккаунту и курсу. Отправлять после восстановления сети; не отправлять очередь старого аккаунта под новой сессией.
- После успешной записи сервер возвращает revision. Обновления нескольких устройств разрешать явно.
- Истёкшая сессия не должна удалять написанный ответ: сохранить локально, предложить войти и продолжить синхронизацию.

### Возвращение после перерыва

Условие: прошло **более 24 часов** с последней содержательной учебной активности этого курса и есть изученный материал. Длительность считать по серверному времени, а не по факту входа в аккаунт.

Перед следующим новым материалом показать:

1. Один короткий абзац: что проходили.
2. Одно-два простых задания по завершённым понятиям.
3. При ошибке — короткое объяснение и возможность попробовать снова.
4. `Continue learning` возвращает на сохранённую страницу, не начинает курс заново.

Сохранить ID повторения, его состояние и время окончания. Перезагрузка не должна бесконечно запускать тот же recap. Повторение не открывает платные уроки и не меняет исходный cursor. Оно может засчитываться как учебная активность один раз.

### Огонёк

Один учебный день — одно значение даты в часовом поясе пользователя. Отображать текущую серию по последовательным учебным дням, учитывая сегодня/вчера. Пустой вход не считается уроком. XP и streak вычисляются по подтверждённым событиям, а не по числу нажатий `Continue`.

## 11. Полный курс, шаблоны и источники

Курс — одна понятная учебная дорога с короткими уроками и сертификатом в конце. Пользователь не должен сначала выбирать внутренние «юниты», инструменты и подразделы.

Минимальная структура сохранённого содержания:

```text
Course: id, contentVersion, title, goal, language, level, mentorId
  Lessons[]: stable id, title, outcome, estimatedMinutes
    Activities[]: stable id, type, explanation, example, prompt,
                  options, validation, feedback, sourceIds, illustration
  Final task: independent practical result and completion criteria
  Sources[]: id, title, url, fetchedAt, asset/attribution metadata
```

Варианты activities: explanation, illustrated-example, single-choice, ordering, matching, short-answer, practical-task, recap. Начать с уже поддерживаемых типов; не генерировать задания, для которых нет рабочего renderer и проверки.

**15 предлагаемых внутренних шаблонов тем:** основы программирования, веб-страницы, таблицы, анализ данных, дизайн постера, рисование, копирайтинг, SMM, презентации, фотография, монтаж видео, английский для повседневных ситуаций, цифровая грамотность, использование AI-инструментов, планирование проектов. Это будущая библиотека шаблонов, а не существующий каталог готовых курсов.

Для каждого шаблона нужны: ID и версия, входные уточнения, последовательность навыков, типы заданий, критерии результата, mentor ID, требования к источникам и финальному заданию. Выбирать шаблон после запроса пользователя; не создавать 15 курсов заранее в его аккаунте.

Рекомендуемый поток генерации: цель → 2–3 уточнения → выбор шаблона → поиск проверяемых открытых источников → план курса → содержание → валидация формата/проверок → сохранение → первый урок. Если цель не поддерживается, честно объяснить это, а не незаметно заменить её другим курсом.

Сохранить ограничения существующего загрузчика URL и проверку источников. Не принимать произвольный URL от модели для серверного скачивания без этих проверок. Источники и метаданные картинок хранить даже при скрытых подписях. Для недоступной картинки предусмотреть понятную иллюстрацию/схему; доступность изображения в интернете не означает разрешение на его использование.

Текущие квоты AI: **10 запросов на IP и 100 суммарно за UTC-день** в одной базе. Генерация и review расходуют общий лимит; несколько пользователей в одной сети делят IP-лимит. Квота не является подпиской. Для курса пересмотреть лимиты по проверенному пользователю и типу операции, защитить от повторных отправок и показывать время/возможность повторной попытки. Ошибка провайдера не должна уничтожать уже готовый курс или ответ.

## 12. Бесплатная часть и demo-подписка

- Один первый курс можно открыть бесплатно.
- Бесплатна примерно первая половина уроков; остальные и создание дополнительных курсов требуют demo-plus.
- Предлагаемое правило: первые `ceil(lessonCount / 2)` обычных уроков, при этом полный курс содержит минимум два урока, а финальное завершение/сертификат требуют полного доступа и прохождения. Зафиксировать правило на сервере.
- `free_course_id` не сбрасывается после архивирования, выхода, нового браузера или деплоя.
- Граница доступа обозначается заранее в плане курса. Не скрывать платное ограничение до последнего клика.
- Demo-активация явно говорит `Demo access — no payment`. Сервер выдаёт demo entitlement по выбранному правилу; произвольное редактирование профиля его не выдаёт.
- Старые готовые примеры сохранить как отдельно обозначенные демонстрационные сценарии, если они нужны для конкурса; не смешивать их с сохранёнными личными курсами.

## 13. Что frontend ждёт от backend

Сайт должен быть простым: один главный следующий шаг, крупные кнопки, короткие тексты. Белый фон, тёплый оранжевый акцент, капибара и персонажи из предоставленной папки. Backend не должен заставлять UI показывать технические детали вместо учебного действия.

| Состояние | Что показывает UI | Какие данные нужны |
| --- | --- | --- |
| Первый вход | Три понятных шага: о себе → интересы → аккаунт | Профиль, завершённость onboarding, состояние подтверждения email |
| Нет курса | `What would you like to learn?` | Пустой список, право создать курс |

| Урок | Один материал или задание за раз | Тип activity, контент, иллюстрация, текущий ответ |

UI связывает их с морганием, движением головы/рук и эмоциями; сервер не управляет кадрами анимации. Неправильный ответ — поддерживающая реакция. При `prefers-reduced-motion` сохраняется понятная статичная поза.

Не ломать существующие hooks: `mindora:account-changed`, `data-course`, `data-step`, `data-choice`, `data-action`, `data-learning-step`, `data-cloud-action`, `#learning-plan-form`, `#learning-step-form`, контейнеры shell и поля редакторов. Подробнее — [TEAM.md](TEAM.md). Пользовательский текст выводить через существующее экранирование.

## 16. Git → Vercel: обновление после коммитов

1. Проверить, какой Vercel-проект связан с `Asizxs33/Mindora` и каким доменом действительно пользуются участники.
2. Production branch — `main`; рабочие ветки публикуются как Preview при настроенной Git-интеграции. [Vercel Git integration](https://vercel.com/docs/git).
3. Сохранить `vercel.json`: `npm ci`, сборка `node scripts/build.mjs`, output `dist`; API обрабатываются отдельно.
4. Переменные должны быть настроены для конкретного окружения и нужного branch scope. Изменение переменной требует нового деплоя для её использования.
5. После push дождаться успешных GitHub checks и Vercel deployment; проверить его commit SHA и статус Ready.
6. Проверить реальный URL в новом браузере: `/api/account`, вход, создание курса, сохранение, повторный вход.
7. Не включать кеширование персональных ответов API; добавить им `Cache-Control: private, no-store`. Для приложения использовать корректное обновление ассетов, а не очистку пользовательского хранилища.

GitHub Actions `checks.yml` запускает проверки, **сам по себе он не настраивает Git-интеграцию Vercel**. Коммит в рабочую ветку не обязан менять production-домен, пока он не вошёл в production branch.

В README сейчас указан `mindora-livid-eta.vercel.app`, отдельно использовались design/другие preview-домены. Перед релизом явно выбрать основной. Данные `localStorage` разных доменов не общие; аккаунтное сохранение должно решать перенос между устройствами на одном продукте.

## 17. Проверки перед передачей готового сайта

### Аккаунт и владение

- [ ] Регистрация → подтверждение email при необходимости → вход → сохранённый профиль.
- [ ] Ошибка сохранения профиля позволяет повторить PUT без повторной регистрации.
- [ ] Возраст/пол можно пропустить; интерес можно добавить своим текстом.
- [ ] Неверный пароль не создаёт видимость входа; выход закрывает приватные данные.
- [ ] Пользователи A и B не получают чужие курсы даже по известному ID.
- [ ] Медленный ответ для A не появляется после переключения на B.
- [ ] После подтверждения email на другом устройстве можно закончить профиль.

### Курсы и сохранение

- [ ] Пустой аккаунт видит создание курса.
- [ ] `New course` сохраняет старый курс; одинаковая цель не мешает создать отдельный курс.
- [ ] Двойной клик/повтор сети не создаёт два курса с одним idempotency key.
- [ ] После обновления страницы сохраняются текст ответа, позиция и показанный feedback.
- [ ] После закрытия и повторного входа курс доступен на другом устройстве.
- [ ] Два устройства не перезаписывают друг друга незаметно: 409 обрабатывается с сохранением черновика.
- [ ] Отсутствие сети и истёкшая сессия не удаляют работу.
- [ ] Старые бюджетные черновики и готовые примеры продолжают работать.

### Обучение и доступ

- [ ] Каждый сгенерированный тип задания умеет отображаться и проверяться.
- [ ] Ошибка AI/429/timeout имеет понятный повтор; готовая работа остаётся.
- [ ] Перерыв > 24 часов запускает краткое повторение и возвращает к прежнему месту.
- [ ] Streak и XP не увеличиваются от перезагрузки или повторной отправки события.
- [ ] Бесплатная граница проверяется на сервере; смена браузера её не сбрасывает.
- [ ] Demo-доступ не списывает деньги и явно обозначен.
- [ ] Сертификат нельзя выдать до завершения; повторное скачивание возвращает тот же документ.

### Интерфейс и публикация

- [ ] Весь основной путь работает на телефоне: регистрация → курс → урок → выход → продолжение.
- [ ] Клавиатура не перекрывает поле/кнопку; все действия доступны клавиатурой.
- [ ] Персонажи меняют позу/эмоцию по действию; reduced motion поддерживается.
- [ ] CI и сборка проходят; production показывает ожидаемый commit.
- [ ] Секреты отсутствуют в Git, клиентском bundle и публичных ответах.
- [ ] Проверены реальные Auth и база, а не только mocked unit-тесты.

## 18. Быстрая диагностика

| Симптом | Что проверить первым |
| --- | --- |
| Аккаунт недоступен, `available:false` | Три настройки Auth/DB в окружении именно текущего deployment |
| Вход успешен, профиль не сохранился | `profilePending`, доступ к DB, повтор PUT после проверки сессии |
| Регистрация требует подтверждения | Реальное email verification; не подставлять локальную фиктивную сессию |
| POST/PUT возвращает 403 | Совпадение origin сайта и API; разрешённые адреса Auth |
| Возвращается старый курс | `state.learningPlan`, `learningPlanOpen`, общий локальный ключ; нет отдельного course ID |
| На другом устройстве пусто | Сохранён ли общий прогресс в базе; текущий бюджетный endpoint не сохраняет остальные курсы |
| 409 при сохранении | Устаревшая revision; получить свежую версию и согласовать, не затирать |
| AI 503 | `DEEPSEEK_API_KEY` и `DATABASE_URL` в правильном окружении |
| AI 429 | Общая/IP-квота или ограничение провайдера; review тоже расходует запросы |
| AI 502 | Ошибка upstream, таймаут или невалидный ответ; сохранить черновик и дать повтор |
| После push сайт старый | Ветка deployment, commit SHA, статус сборки, нужный Vercel-проект и домен |

**Готовность продукта означает проверенный путь пользователя, а не только успешную сборку.** Авторизация уже есть; следующая ключевая работа — связать с ней курсы, ответы, продолжение, учебные дни и сертификаты.
